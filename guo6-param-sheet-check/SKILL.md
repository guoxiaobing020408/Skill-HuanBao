# 国六环保样品参数表核对

把「重型柴油车样品参数表（国六环保）」的填写从逐字段翻报告，改成先出一张核对表、你点头之后再写进参数表。

## 什么时候用

用户要给某台改装车填国六环保样品参数表，手上有一套视同报告（一份噪声、一份排放/PEMS），希望核对哪些字段从报告取、哪些必须人工填。

## 这个技能管什么

- 从两份视同报告里把参数表的字段一个个对出来，标清每个值的出处。
- 自动填两类：① 发动机参数（含润滑油、反应剂）、变速箱参数、污染物控制装置参数——取自两份报告；② 报告里有且两份一致的整车字段，如隔音材料。
- 整车参数、底盘参数里报告给不出准数的，按「依据文件」列指明去哪份材料上抄（底盘合格证、整车合格证/铭牌、公告、实车），不替用户填。报告里的同名字段只是基准车数据，仅作参考。
- VIN 号、发动机编号属于本表不填项，留空即可，不列进待填清单。
- 两份报告值不一致、规则又没写明的，不替用户决定，单独列出来。
- 每个自动写入的值都能追到「哪份文件、哪个栏目的哪一格」，并出一份 Word 核对表。
- 写表只写副本，原件不动。

## 输入

| 输入 | 说明 | 必需 |
|---|---|---|
| 参数表 | 重型柴油车样品参数表（国六环保），同时充当模板和单元格位置依据 | 是 |
| 排放视同报告 | 文件名一般含 PM6，PEMS／实际道路车载法排放报告 | 是 |
| 噪声视同报告 | 文件名一般含 ZS6，加速行驶车外噪声报告 | 是 |
| 规则表 | `references/field-rules.tsv`，技能自带 | 是 |
| 底盘合格证 | 底盘厂出的合格证（或一致性证书）：底盘型号、名称、生产厂、分类、最高设计车速、轮胎规格/数量、驱动形式、总质量、发动机型号、VIN、整备质量 | **是** |
| 整车合格证／铭牌 | 改装厂整车合格证或铭牌：车型名称、生产厂、生产日期、外形尺寸、整备质量、乘员数 | 建议 |

文件格式：`.docx`，或扩展名是 `.doc` 但实际是 docx 包（可用 `zipfile` 打开）。真正的 Word 97 二进制 `.doc` 会读不出表格，按「停止条件」处理。

## 换车型怎么用

每台车换一套输入，规则表不动。`references/field-rules.tsv` 里只有通用规则（哪个字段看哪份报告、按什么方式取值），不含任何具体车型、具体数值——任何时候都不要把某一台车的值写进规则表。

换车型时只改三处：参数表换成该车型的模板、两份视同报告换成该车的、输出目录按车号分开。参数表结构不变时脚本无需改；遇到栏目名不同的新版参数表，改规则表里的字段名即可，不改脚本。

## 第一步 确认输入

1. 确认三个文件都在，且两份报告一份管排放、一份管噪声。判断方法：报告首页标题含「实际道路车载法排放」的是排放报告，含「加速行驶车外噪声」的是噪声报告。
2. 确认参数表是国六环保那一版（表格里含「污染物控制装置参数」和「OBD型号及厂家」）。
3. **要底盘合格证**。规则表里人工字段有 8 个的依据就是底盘合格证（底盘型号/名称/生产厂/分类、驱动方式、最高设计车速、轮胎型号、轮胎数量），没有这份材料，这些格子只能空着。用户没给就先要，别拿报告里的基准车数据充数。
4. 报告类型搞反时不要继续，先跟用户确认哪份是排放、哪份是噪声。

合格证可以是图片（jpg/png）或 pdf，用读图能力逐项看，不要求做成表格。整车合格证/铭牌同理，一并要最好。

## 第二步 生成核对表

在技能目录下执行（`$SKILL` 指技能根目录，可用脚本的相对路径）：

```bash
python scripts/build_audit.py \
  --sheet "<参数表路径>" \
  --pm "<排放报告路径>" \
  --zs "<噪声报告路径>" \
  --rules references/field-rules.tsv \
  --out-dir "<输出目录>"
```

产物：

- `audit.md`：给人看的核对表，五节——逐字段核对、待你填写、两份报告不一致、报告里找不到、与表内现值的差异；不填项在第二节末尾单列一行提示。
- `audit.json`：给填表脚本用的结构化结果。`meta` 里记着三份输入的文件名与两份报告的编号；每个字段除取值外还带溯源信息：`src_kind`（`pm`/`zs`/`pmzs`，说明取自哪份报告）、`src_section`/`src_field`（报告里的栏目路径）、`src_cands`（两份报告各自的原值，冲突时用来对照）、`tbl`/`row`/`col`（单元格位置，`tbl` 是参数表在文档里的第几张表，写表必须三个一起用，缺一不可）；人工字段还带 `basis`（依据文件，如「底盘合格证」）、`ref`（两份报告参考值一致时的那个值）、`ref_text`（展示用，两份不一致时形如 `A 排放:1-3 / B 噪声:2-3`）与 `ref_cands`（两份报告各自的参考值）。参考值一律两边都取，不要只取排放报告——两份报告的基准车可能不是同一台，只给一边会藏住口径差异。第六步的来源核对表直接读这些字段，不要另外拼来源。

判定含义：

| 判定 | 含义 | 写表时 |
|---|---|---|
| 自动 | 来源唯一或两份报告一致 | 直接写 |
| 自动·待核对 | 报告一致，但按规矩还要跟实车/铭牌核一遍（发动机、变速箱型号类） | 先写，提示核对 |
| 人工 | 只能人工判断，报告里的值仅作参考 | 不写 |
| 不填 | 本表不填（VIN 号、发动机编号） | 保持空 |
| 冲突待定 | 两份报告不一致且没有裁决规则 | 不写，交用户定 |

人工字段的「依据文件」列说明这一格该去哪份材料上抄：底盘合格证（底盘型号、生产厂、分类、最高设计车速、轮胎规格/数量）、整车合格证/铭牌（车型名称、生产日期、外形尺寸、整备质量、乘员数）、公告、实车。遇到用户说某字段从合格证/铭牌来的，改的是规则表这一列，不是挨个改脚本。
| 报告缺此项 | 规则要求取数，但报告里找不到该栏 | 不写，交用户定 |

统计行会打印五类各多少项。缺项或冲突不为零时，在交付里逐条说明，不能悄悄跳过。

## 第三步 交付核对表

1. 把 `audit.md` 第二节「待你填写的字段」直接呈现给用户，这是他要动手的部分。表里带「依据文件」与「报告里的参考值」两列：前者说去哪份材料抄，后者只是基准车数据，两者不同不算错。参考值一律列两份报告（两份不一致时写 `A 排放:… / B 噪声:…`），不要只报排放报告那一份。
2. 把第三节「两份报告不一致」和第四节「报告里找不到」单独提醒，请用户给结论。
3. 有了底盘合格证/整车合格证，就把第二节里「依据文件」指向它们的字段逐项读一遍：与合格证一致的，交付里直接写「与合格证一致」；不一致的，单列成「表内值 vs 合格证值」请用户定。这是给结论、不是改表，人工字段仍然不替用户写。
4. 明确说一句：核对表里的建议取值全部有出处，人工项一个都没替用户填。
5. 等用户确认后再进入第四步。用户没确认就不要写表。
## 第四步 写进副本

先预览，再写盘：

```bash
python scripts/fill_sheet.py --sheet "<参数表路径>" --audit "<输出目录>/audit.json" --out "<车号>_样品参数表_<YYYYMMDD>.docx"
```

不加 `--apply` 时只打印将写入的单元格，不产生文件。用户确认后加 `--apply` 生成副本。

用户当场给的人工值用 `--set` 补，可重复，格式 `字段=值` 或 `分段/字段=值`。字段名在参数表里重名时（例如「生产厂」整车、底盘各一个，「型号」变速箱、底盘各一个）必须写成 `分段/字段`，只写字段名会被拒绝并列出候选，不会替你挑一个：

```bash
python scripts/fill_sheet.py --sheet "<参数表>" --audit "<输出目录>/audit.json" \
  --out "<车号>_样品参数表_<日期>.docx" --set "车辆型号名称=<公告型号+车辆名称>" --apply
```

模板里残留上一台车的人工值时，先按核对表第二节逐条比「表内现值」和「参考」；确认要清空的加 `--clear-manual`（只清人工字段，不清自动字段）：

```bash
python scripts/fill_sheet.py ... --clear-manual --apply
```

硬性要求：

- 输出路径必须与原件不同，脚本会拒绝同路径写入。
- 只写「自动」「自动·待核对」两类字段，外加用户用 `--set` 明确给出的字段。
- 其余人工字段一律不动，留给用户按核对表补。
- 副本已存在时不覆盖，除非显式加 `--force`。

## 第五步 核查成品

写表之后必须再核一遍，不能跳过：

```bash
python scripts/verify_sheet.py --sheet "<副本路径>" --audit "<输出目录>/audit.json" --out "<输出目录>/verify.md"
```

退出码 0 表示无错误，1 表示有错误，2 表示输入缺失，3 表示参数表读不出结构（未生成核查报告）。报告分两类：

- **错误**：必须改。包括自动字段回读与报告取值不一致、自动字段为空、基准质量不小于最大总质量、轮胎数与驱动方式对不上、速比个数与档位数对不上、净功率大于额定功率、后处理型式写了某个装置但该装置栏是「——」、汽车分类与总质量档位矛盾、车型名称直接抄了报告的基准车型。
- **警告**：请用户确认。包括人工字段仍为空、依据指向报告的人工字段与报告参考值不同、型号与厂家没按「型号/厂家」写、未安装项没统一成「——」、后处理型式未提及但装置栏有型号。依据是底盘合格证/铭牌/公告的字段，与报告值不同不再报警告——本来就不是一个来源。

有错误时先定位是写表问题还是人工填写问题：回读不一致属于写表或报告解析问题，回到第四步重跑；业务矛盾属于数据本身问题，交用户确认后再改。

## 第六步 出数据来源核对表

用户拿到的参数表里只有值，看不出这个值是从哪份文件抄来的，人工核对无从下手。每次交付都要给一份 Word：

```bash
python scripts/make_source_doc.py --audit "<输出目录>/audit.json" \
  --sheet "<副本路径>" --vehicle "<车型>" --out "<输出目录>/数据来源核对表.docx"
```

`--sheet` 传刚生成的副本，脚本会把表内实际值读回来，与核对表建议值逐条比对，一致/不一致直接标在纸面上。不传 `--sheet` 也能出表，但「与表内」一列会退化成「—」。

生成的 Word 共八节，横向 A4，可直接打印签字：

| 节 | 内容 | 给人解决什么 |
|---|---|---|
| 一 | 文件清单：代号 A/B、文件名、报告编号、各自职责 | 先分清哪份是哪份，不会拿错 |
| 二 | 怎么核对这张表（5 条读法） | 拿到表的人不用问就知道怎么用 |
| 三 | 自动写入字段逐条溯源：序号、分段、字段、写入值、来源（A/B/A+B）、报告位置、判定、与表内是否一致 | **核心节**，每个值都能对到报告原件 |
| 四 | 人工填写字段清单：当前值、**依据文件**（去合格证/铭牌/公告哪一栏抄）、写法 | 知道哪些格子还空着、该翻哪份材料 |
| 五 | 两份报告不一致的字段，A、B 两列并排 | 一眼看出差在哪 |
| 六 | 两份报告都查不到的字段，附找过的位置 | 知道系统确实没找到，不是漏了 |
| 七 | 本表不填、保持留空的字段 | 免得有人以为漏填 |
| 八 | 字段统计 | 数量对得上 |

「报告位置」不是笼统写「排放报告」，而是写到栏目路径，例如 `发动机 › 最大净功率/转速(kW/r/min)`、`污染控制装置 › 喷油泵`、`变速箱 › 速比`；燃料表类写 `润滑油 › 生产厂`。用户照着这一栏翻报告，能直接定位到那一格。

第三节「与表内」出现「不一致」或「表内为空」时，说明写表与核查的结论对不上，先查清楚再交付，不能带着矛盾交出去。

## 第七步 交付前自检

1. 核查报告 `verify.md` 的错误数为 0；警告逐条看过并已向用户说明。
2. 副本能正常打开，表格没有错位，值落在对应格子里。
3. 抽查三处：一个只在排放报告有的字段（如喷油泵）、一个只在噪声报告有的字段（如排气管）、一个两份都有且一致的字段（如排气管之外的 DOC）。
4. 人工字段仍是空或原值，没有被脚本改动。
5. 报告缺项、冲突项在交付说明里都提到了。
6. 底盘合格证要到了，依据指向它的 8 个字段都已逐项比对，一致的说了「与合格证一致」，不一致的列出了「表内 vs 合格证」。
7. `数据来源核对表.docx` 已生成，第三节条目数等于自动写入的字段数，且没有「不一致」「表内为空」的红字行。
8. 明确告诉用户：填了哪些、留了哪些、哪些要他定、核查查出什么、数据来源表在哪。
9. 模板里若有上一台车的残留值，逐条点出「表内现值」与「参考值」不一致的人工字段，提示用户改或清空。

```markdown
## 四、写表结果

```

## 停止条件

- 参数表或任一份报告读不出表格结构：脚本会以退出码 3 停下并说明原因，此时不得继续，也不要手工补一张核对表。典型原因是文件为真二进制 `.doc`，请用户用 WPS／Word 另存为 `.docx` 后重跑。
- 参数表与规则表的字段匹配率低于一半：说明不是同一版参数表，停下向用户确认，不要按剩余字段凑一份结果。
- 两份报告的发动机型号不同：属于不同机型，不能视同，停止并告知用户。
- 两份报告的汽车分类一个是城市车辆、一个不是：先让用户解决分类冲突，再填表。
- 用户要求的填表方式与「只写副本」冲突时，先说明风险再按用户明确指令执行。
- 没有底盘合格证：底盘参数与整车里的合格证类字段一律留空，交付里写明「缺底盘合格证，8 个字段无法核」并要求用户补件；不许用报告里的基准车数据顶替。

- `references/field-rules.tsv`：67 个字段的来源、取值处理、说明与**依据文件**（该去底盘合格证/整车合格证/铭牌/公告/实车哪一栏抄），脚本直接读它，改规则只改这里。`取数方式` 只允许五个值：`排放`（只查排放报告）、`噪声`（只查噪声报告）、`两款`（两份都查，一致才用）、`人工`、`不填`；写别的值脚本会报错停下，不会被当成人工悄悄放过。
